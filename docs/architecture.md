# Foundation decisions

## Distribution and development

Ship one npm package containing the Node CLI/runtime and built static React UI. Use pnpm for development, Vite's official React plugin and Tailwind integration for the UI, and TypeScript for strict checking and Node output. Avoid adding a second bundler before the small CLI needs one. Build artifacts are generated under `dist/node` and `dist/ui`; UI build dependencies do not need to be installed by package consumers.

## Portable domain ownership

Factory definitions belong to `.code-factory`. Agent-native files are import/export representations handled through a separate translator registry, independent of execution adapters. Existing `.kiro`, `.cursor`, `.claude`, and project instruction files remain user-owned. Translators report unsupported or lossy fields, preview changes, and preserve existing content. Cursor project rules and Kiro workflows are currently supported; the other native providers and instruction files require their own schemas and translators.

### Native configuration translation

Supported formats are `cursor-rule-mdc` (import/export) and `kiro-workflow-json` (import-only). A Cursor import or export handles one Cursor project rule at `.cursor/rules/<name>.mdc`. Cursor's [project rules schema](https://cursor.com/docs/rules) uses YAML frontmatter (`description`, `globs`, `alwaysApply`) followed by Markdown instructions. The importer accepts a conservative, single-line scalar frontmatter subset, requires `description` and a nonempty body, rejects duplicate or malformed fields, and reports every field besides `description` as unsupported. `globs` and `alwaysApply` affect Cursor activation and have no portable scheduling equivalent. The body becomes the instruction of one agent step in an empty V2 draft; the description becomes the loop and step name. No execution binding or connection is inferred.

Export requires a valid draft whose first step is an agent step with nonempty instructions. It renders that step's name and instructions as `description` and Markdown body, with `alwaysApply: false`. Additional steps, graph structures, policy and step metadata are reported as semantic losses. Cursor activation is always reported as a loss. Native import/export conveys configuration only; it cannot authenticate, execute, steer or synchronize an agent.

The UI lists formats from the translator registry. Preview includes the affected path, conflicts, rendered content or imported step, and structured loss report. Applying import only updates the editor draft; the user saves it through the normal `.code-factory` flow. Export creates a new native rule only and never overwrites an existing file. A preview revision binds the validated draft and native file content; application rechecks it. Names are restricted to simple path components. Native file access requires Python 3 on a POSIX host so each path component can be opened relative to a pinned parent directory with `O_NOFOLLOW`; unavailable support fails closed. Export uses exclusive creation in the pinned directory. Malformed input, incompatible portable schema versions, changed previews, linked paths and existing native rules fail without replacing user files. There is no automatic synchronization in either direction.

`kiro-workflow-json` imports one Kiro workflow recipe at `.kiro/workflows/<name>.workflow.json`. It is import-only and configuration-only: nothing in the recipe is executed, no agent is authenticated, and no execution binding is inferred. `GET /api/native/formats` lists each format's `directions` (`["import", "export"]` or `["import"]`), the UI disables Export for import-only formats, and an export preview or apply for Kiro is rejected with 422 before any file access. Decisions:

1. Import requires an empty draft, as for Cursor; otherwise the request fails with 422 and the draft is unchanged.
2. Only the project-relative directory is read, through the same no-link, 1 MB-limited native file access. Global recipes in `~/.kiro/workflows` are not read; copy one into the project first (`mkdir -p .kiro/workflows && cp ~/.kiro/workflows/<name>.workflow.json .kiro/workflows/`).
3. A Kiro `repeat` becomes a repeat group. The importer adds a `<repeat>-decision` agent step after the last body step; it carries the decision with outcomes `stop` (leave the group) and `continue` (re-enter at the first body step). The scheduler fails a decision step whose whole output is not a declared outcome, so the last Kiro step keeps its own prompt, stage and output contract, and the generated step reads that step's output and returns only the outcome. The Kiro stop condition is not evaluated by Code Factory: its JSON is kept in the decision step's instruction (up to 8,000 characters; a longer rule is cut and reported) and reported as lossy. On `continue`, the first body step receives the decision outcome, not the last Kiro step's output. When the repeat has no single successor (for example it ends the workflow or is followed by a parallel), a `<repeat>-exit` step is added as the exit target, because repeat groups need an exit branch outside the body. It is an agent turn with a pass-through instruction rather than a `check`, since a check runs a host command. Both generated steps have the role `Importer generated`, a name ending in `(importer generated)`, a lossy report entry, and a "Generated by importer" mark in the preview. Nested repeats and repeats that do not start and end with a single step are rejected with the source path.
4. Every Kiro `step` becomes an `agent` step: the Kiro id is normalized into a loop id, `agent` becomes the role, and the prompt is kept verbatim as the instruction. A stage is inferred only from whole tokens of the agent and id (`review`/`reviewer` → review, `reader` → evidence, `design`/`plan` → planning, `implement`/`integrate` → implementation).

`sequence` nodes become dependency chains. A `parallel` becomes fan-out edges and an `all`/`any` join on each following step; it is a semantic parallel group only outside repeats and only when every branch is a single step, because a step belongs to at most one group (a parallel inside a repeat stays fan-out/fan-in with a lossy issue). `allSettled` is imported as `all`. The scheduler starts one ready non-review step at a time, so a parallel with non-review steps runs its branches one after another and is reported as lossy. An `any` join is ready once one branch succeeds, but the other branches are not canceled and review steps started together are awaited as a batch; this is also reported. A review step inside a repeat that returns `changes-requested` rejects the run instead of starting another round, and is reported. Kiro `onMaxIterations` `continue` and `pause` have no equivalent: like `abort`, the run is rejected when the round limit is reached, and the report says so. Kiro `modelId` and `effortLevel` (including workflow defaults) are appended to the instruction as an import note and never bound. Unknown keys on the root and on nodes are reported as unsupported and ignored, so recipes from newer Kiro versions still import; unknown keys inside `stopCondition`/`fileCheck` are rejected because they would change the stop rule. The report also covers `description`, `inputs`, `artifacts`, `captureOutput`, `completion`, `watch` nodes, id changes, `onMaxIterations`, iteration counts above 10 (clamped), and `{{…}}` template references, which are kept verbatim and not substituted. Imported steps have no expected outputs or bindings; add them in the editor before publishing. Code Factory counts implementation rounds across all repeat groups of a run against `maxImplementationRounds`, so a second repeat shares that budget and is reported as lossy. Before schema validation the parser bounds node nesting (16 levels, 500 nodes) and every JSON value, free-form fields such as `stopWhen`, `config` and `completion` included (64 levels, 20,000 values), so hostile input fails with 422 instead of exhausting the stack. Import failures caused by the file are prefixed with its project-relative path and keep field paths. A multi-step import preview lists every step with its instruction in a disclosure, so the prompts an agent will receive can be read before applying.

The V2 portable schema describes agent/check steps, explicit dependency edges, semantic parallel/repeat groups, joins, decisions, separate canvas positions, execution bindings, output declarations, retry limits, and total implementation-round limits. Repeat groups require a bounded iteration count, an exit branch outside the group, and a distinct continuation branch into the group. The continuation is a semantic back edge; ordinary dependency cycles remain invalid. The two-round advanced policy means initial implementation plus one repair. It does not mean two additional repairs. Policy fields alone do not implement repair scheduling.

Keep roles/instructions independent of provider/model bindings. Resolve defaults into a run snapshot once. The local registry stores drafts at `.code-factory/loops/<id>/draft.json`, immutable numbered publications at `versions/<version>.json`, and runs at `.code-factory/runs/<run-id>.json`. A publication advances the editable draft to the next version. Invalid imports and corrupt files fail with their path and validation details rather than resetting saved data. V1 loop and detached run snapshots migrate to V2 on parse; no previous persisted run format existed.

Run records retain detached task, loop/version, project default, per-step resolved bindings and baseline identity. Every run, step instance, attempt and implementation round has a durable UUID. Sibling steps have separate status and attempt histories. Retrying a step increments its attempt number without advancing the implementation round; repair appends a round record explicitly. Native session and turn resume handles may be attached once to a running attempt. Evidence entries define events, guidance, checks, reviews, outputs, files and artifacts with provenance and candidate freshness. Guidance transitions can append receipts sharing a message ID. File and artifact references use validated project-relative paths. The storage layer enforces immutable snapshot identity, append-only evidence, revision checks and retained attempt and round identities. The scheduler claims ready steps before launching an adapter, records native session IDs and events, and persists separate candidate and input hashes.

Public events have contiguous per-run sequence numbers and retain their step, attempt, session and turn identity. Cursor replay and server sent events read the persisted run record, so closing a browser subscription does not control execution. Agent messages, supported public tool output, local checks and lifecycle changes are separate event types. Native reasoning notifications are excluded. A transport error after launch leaves an interrupted attempt and an unavailable run instead of inventing a provider failure. After service restart, a run with a persisted completion event can settle that attempt. An active native attempt can reattach only when its adapter declares verified resume support and has durable session and turn handles. Check processes and review workspaces that did not persist completion cannot resume. Unsupported or uncertain recovery records an interruption and never starts another paid attempt automatically. Historical attempts and queued guidance remain append-only.

## Execution ownership — confirmed for the first adapter (THI-6)

Code Factory owns the portable loop scheduler. The Codex adapter starts one app-server thread and turn for one assigned step; retry starts a separate thread for that step and attempt. The adapter does not submit a graph to a native workflow runner. Do not simultaneously schedule the same graph through a native workflow runner. Delegated native workflow execution would be a distinct mode with explicit ownership.

The fixture validates this ownership and preserves run, step, attempt, thread, and turn identities on every portable event. The scheduler uses the same adapter contract for mock and verified native turns; run updates store event, check, and review receipts before moving to dependent work. Native subagents inside an assigned step remain provider behavior and do not automatically become factory graph nodes.

## First native adapter proof boundary

Codex CLI 0.160.0 is the first candidate. Its locally generated app-server protocol schema includes `initialize`, `account/read`, `model/list`, `thread/start`, `turn/start`, `thread/resume`, `thread/read`, and `turn/steer`. The adapter uses JSON-RPC over a private stdio process. `item/agentMessage/delta` and `turn/completed` become portable step events. `turn/steer` uses the expected active turn ID and never calls `turn/interrupt`. The native process owns credentials; connection inspection returns only an authentication state and a display catalog. A catalog entry is not proof of entitlement to run that model. The factory does not read or export credential files.

Kiro CLI 2.27.1 has a separate execution adapter using its v2 `chat --output-format stream-json` event stream. It maps one CLI invocation to one portable step and verifies a successful process exit before completing that step. The factory passes only `fs_read` and `fs_write` as trusted tools. Kiro authentication is checked through the CLI's `whoami --format json`; credentials remain native. This stream invocation has no tested reattachment or cooperative guidance path, so the adapter declares resume and steering unsupported and keeps effort choices unavailable because its model catalog does not advertise supported effort values. Model choices come from validated `chat --list-models --format json` catalog entries; selected IDs are forwarded through `--model`, while `agent-default` leaves the CLI default intact. Paired native runtime evidence records the same portable loop and task snapshot through Codex and Kiro. See [Kiro ACP](https://kiro.dev/docs/cli/acp/) and [Codex app-server](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server).

A host-authorized disposable-project proof on 2026-10-03 completed with Codex CLI 0.160.0 and `gpt-6-sol`. The [native receipt](evidence/thi6-native-2026-10-03.json) records authenticated catalog inspection, actual text-file edits, started/message/completed events with stable identities, a `turn/steer` acknowledgment plus the requested file, completed-turn recovery after a new app-server connection, and a selected retry on a distinct thread after an intentionally unavailable model produced a native error. No `turn/interrupt` was sent. Factory scheduling remains the sole graph owner.

The proof exposed two integration gaps: incoming server requests were discarded as responses, and the turn lacked explicit writable roots. The adapter now supplies its assigned project root with native tool network access disabled, declines command approvals, and rejects unsupported server requests. A host may supply an explicit file-change decision callback; the proof accepts only patches to its three allowlisted disposable files. Production UI approval handling is still a separate integration task. Connection capability declarations remain `unknown` until connection-specific evidence is verified; this one host receipt is not a blanket claim for every executable, account, model, or machine.

Run `pnpm prove:codex` only with explicit native launch intent. It makes bounded real model calls, uses Codex-owned authentication, preserves the disposable project and receipt for inspection, and exits nonzero if any required check fails. The initial pre-initialize sandbox failure is historical; it no longer describes the current host after the runtime permissions were granted. Fixture tests remain separate from the native receipt. [Supported app-server lifecycle and approvals](https://learn.chatgpt.com/docs/app-server).

## Connection truthfulness

### Cooperative guidance boundary

`POST /api/runs/:runId/guidance` accepts a `stepId`, durable `attemptId`, and nonempty `message`. The runtime validates that the attempt belongs to the step, appends a queued guidance receipt to that exact run, and sends it only through the active attempt's native session and turn. A successful `turn/steer` response records delivery; it does not count as an agent acknowledgment. Acknowledgment requires an agent message containing the guidance message ID after the queue receipt, and records the reply event ID. Undelivered guidance retains a reason when its attempt ends. Connection loss or unknown/unsupported steering rejects a new send before queuing, allowing the UI to keep its draft.

The first native steering proof is limited to Codex CLI 0.160.0. Other versions expose steering as unknown until verified. The current portable runtime has no pausing/paused state and no waiting-for-input prompt or answer method. An input answer must use a separate adapter-supported request/reply control, tied to the waiting prompt and attempt; it must never be sent through ordinary `turn/steer`. The UI does not offer a reply control without such a verified path.

An executable candidate is not an authenticated or supported connection. Discovery performs no agent launch and reads no credentials. Identity/version verification, supported interfaces, authentication, advertised capabilities, and model catalogs must be proved by each runtime adapter. Generic executable names such as `agent` need particular care during verification. UI controls consume capabilities, rather than assuming parity from brand names. Custom connections will require explicit executable and protocol configuration.

The connection registry now launches Codex only after an explicit local verification request. A custom path uses the same supported Codex app-server protocol and must pass executable, identity, and inspection checks; a saved path by itself never becomes a connection. The runtime keeps verified sessions in memory and stores only project defaults and optional custom executable configuration. Catalog choices are validated at save time. Previously saved unavailable selections remain visible in the UI and cannot silently become another model. Per-step binding selectors are exported for the loop editor; run snapshots continue to resolve bindings once at creation.

The mock emits started/message/completed events and supports cancellation. It declares no steering or resume. A successful mock step means only that the fixture completed; it creates no source edits or test evidence.

## Local runtime and UI state

Run intake uses the CLI-selected project only. It reads an actual immutable published loop version, checks every resolved binding against the current verified connection catalog, retrieves ticket material on the server when requested, and writes a pending run with the returned UUID as an idempotency key. A repeated request with that UUID returns the saved run; a changed payload conflicts. No scheduler starts at intake time.

Each new run works in the selected project itself (`baseline.workspace` is `.`). Intake refuses a project that is not a Git repository root, has no commit, has an operation in progress (merge, rebase, cherry-pick, revert or bisect), or has any uncommitted change: `git status --porcelain --untracked-files=all` with `:(exclude).code-factory`, so ignored files and Code Factory's own data do not count. It then runs `git switch -c <name>` at HEAD, which refuses an existing name, so a branch is never reused or overwritten; the name defaults to the ticket ID or `code-factory/<first 8 hex of the run id>` and is validated by the domain and `git check-ref-format`. The baseline records the branch and `checkout.previousBranch`/`previousRevision`. A per-project start lock plus a persisted check (no other in-project run that is not terminal) means only one run holds a project; a pending run can be canceled to release it. If storing the record fails, intake switches back and deletes the branch only while it still points at its start commit. Execution is refused, without changing the run, unless the checkout is on the run branch, and a first execution also requires a clean tree; each step re-checks the branch and fails with `checkout-moved` evidence rather than run against another branch's files. All steps run with the project as their working directory, so agents use the project's own configuration, including untracked and ignored files. After every successful attempt of a non-review agent step that changed files, the runtime (not the agent) commits on the run branch with the user's Git identity (`-c user.useConfigOnly=true`, never a config write) and normal hooks; the message carries `Code-Factory-Run`, `-Step`, `-Attempt` and `-Round` trailers, and `.code-factory` is excluded from `git add`. A hook rejection, or a checkout no longer on the run branch, is recorded as `commit-failed` evidence and fails the step. Reviewers are read-only by enforcement where the provider supports it: the portable step input carries `readOnly`, which Kiro maps to `--trust-tools=fs_read` and Codex to the `read-only` thread sandbox and `readOnly` turn policy with every command approval declined; the project tool grant never applies to a reviewer. Reviewers and checks are also verified, not isolated: each records a per-file hash of the tracked and non-ignored untracked files before it starts and fails with `read-only-violation` evidence (or a failed check summary) listing every added, modified or deleted path afterwards; nothing is reverted. Parallel reviewers share the folder, so one reviewer's change fails all reviewers running at the time. Candidates are hashed from `git ls-files --cached --others --exclude-standard` plus each file's executable bit, so ignored caches and dependencies do not change candidate identity. Read-only probes that the UI polls (status, diff, file list) never take `index.lock`: status runs with `--no-optional-locks`, and diffs run against a private copy of the index, so polling cannot make a step commit fail. While the checkout is on another branch, live file inspection and acceptance report the run's files as unavailable instead of showing the other branch. After the run is terminal, "Back to <branch>" is a plain `git switch` to the previous branch (or `--detach` at the previous revision), refused with any uncommitted change, so nothing is stashed, reset or overwritten. Promotion creates a branch at the run branch tip with `update-ref <ref> <sha> ""` after explicit acceptance of the current candidate and with a clean tree, never switches the checkout, and is unnecessary when the run branch already has the ticket name. Every mutating Git command lives in `src/runtime/run-branch.ts`; Git config is never written and nothing is pushed. An optional argv `setupCommand` from `.code-factory/project.json` runs once in the project before the first step, without a shell, recorded as run-level setup evidence; a failure fails the run before any agent step. Runs created before in-project execution keep working from their stored workspace and are never migrated: worktree runs (`../<repo>-code-factory/<runId>` on `code-factory/<id>`) keep their frozen reviewer clones, removal and promotion, and legacy clone runs (`.code-factory/workspaces/<uuid>`) keep their walk digest and copy-based reviewers. New runs never create a worktree or clone. Non-Git projects cannot start a run.

Bind to loopback and serve the packaged UI from its installed directory, independent of the user's project directory. Reject foreign Host/Origin headers and unsupported mutations. Filesystem paths come from the CLI-selected workspace, rather than arbitrary browser input. Future mutation endpoints require explicit validation, ownership, and concurrency controls.

Keep local React state near its components. Use reducers for complex editor transitions; add server-state caching when runtime endpoints exist. The backend's durable run state will remain authoritative. Do not duplicate execution ownership in UI state or simulate model acknowledgment without an actual provider reply.

The loops library reads saved drafts and the latest publication from the local registry. The five-stage board is a view of portable steps; `stage` and canvas coordinates do not grant execution order. Explicit before/after targets change dependency edges, while group, join, and decision controls change their corresponding portable structures. The editor keeps immutable undo/redo states, saves drafts through the runtime, and validates publication against current connection catalogs and project defaults. Publications stay numbered and immutable; later edits target the next draft version. Optional templates and import/export are owned by THI-18.
